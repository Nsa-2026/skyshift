Architecture

Photos stay in the cloud, laptops only hold code

NASA's SPHEREx photos sit on Amazon's servers in North Virginia and anyone can read them without an account. Our Google machine in the same area streams them, keeps only the measurements, and the website reads those.

Deep zone, in bulk

The worker machine claims a batch of 100 photos, streams only the parts it needs from Amazon, measures every dot, writes a Parquet file to Cloud Storage and moves on. Nothing is kept on disk, and a restart continues where it stopped.

Any spot, on demand

The API asks NASA's archive which photos cover the spot, downloads small cutouts, stacks them per detector and pass, and returns PNG frames. Results are cached in Cloud Storage.

The website

A static site on Firebase Hosting. Requests to /api go to Cloud Run on the same address, so there is no cross-site setup. Votes go straight to Firestore.

€264 credit already active on a full account, valid until January 2027. One bill, one set of tools. Reading NASA's Amazon copy anonymously costs us nothing.

CLAUDE.md (repo root)
# SkyShift

Web tool for NASA Space Apps 2026 "Planet X and SPHEREx": browse NASA's SPHEREx infrared sky,
blink photos of any spot across sky passes, and hunt moving or changing objects.
Concept plan: docs/skyshift-hackathon-plan.html

## Areas and owners
- pipeline/  Python. SPHEREx photos (s3://nasa-irsa-spherex, anonymous) → dots → objects → suspects (Parquet). Owner P1.
- server/    Python FastAPI on Cloud Run. Blink frames on demand, object details, suspects. Owner P2.
- web/       Vite + TypeScript. src/app, sky, card, api, data → P3. src/blink, vote → P4.
- contracts/ Source of truth for every interface. Owner P1 (lead).
- fixtures/  Small real samples. Use them in tests and until real endpoints exist.
- infra/     Cloud scripts. worker/ → P1, run/ and firebase/ → P2.

## Rules
- Stay inside your area's folders. If something outside must change, say so in the PR description.
- Never edit contracts/ in a feature PR. Contract changes are their own PR, reviewed by the lead.
- Match the contracts exactly: names, types, units (degrees, arcsec, µm, MJD) and the pass rule.
- Keep tests passing: `uv run pytest` in pipeline/ and server/, `npm test` in web/.
- No secrets in the repo. Google credentials come from gcloud; anything else goes in .env (gitignored).
- Small working steps. Commit when tests pass.

## Domain facts
- SPHEREx has 6 detectors: D1 0.75–1.1, D2 1.1–1.6, D3 1.6–2.4, D4 2.4–3.8, D5 3.8–4.4, D6 4.4–5.0 µm.
  17 colour channels each = 102. One pixel ≈ 6.15 arcsec. Photos are 2040 × 2040.
- A photo file has parts IMAGE, FLAGS, VARIANCE, ZODI, EPSF, WCS-WAVE. We only read IMAGE, FLAGS, WCS-WAVE (~28 of 65 MB).
- Each spot is seen at a different wavelength in every photo: compare brightness only within one detector.
- Archive collections: spherex_dr1 (Apr 2025–May 2026) and spherex_qr3 (May–Oct 2026). Skip *_deep.
- Test objects (web/src/data/targets.json): Barnard's Star, Epsilon Indi B, WISE 0855−0714, RW Aurigae, R Draconis.
  Fast movers must be corrected for proper motion: Barnard's Star is ~4.5 arcmin from its year-2000 position.
- Docs: IRSA SPHEREx tutorials https://caltech-ipac.github.io/irsa-tutorials/spherex/

contracts/dots.md · the dot table

ColumnMeaning
photo_idIRSA observation id plus detector, e.g. 2025W17_4B_0001_1D1
detector1–6
mjd · passTime of the photo (MJD-AVG) and sky pass number
ra · decSky position, degrees
x · yPixel position in the photo
flux · flux_errBrightness and its error, µJy
wavelength_umColour the pixel saw, from WCS-WAVE
snr · flagsSignal-to-noise; OR of flag bits under the dot
hp32HEALPix tile, nside 32, nested (~1.8°). Used to split work

Derived tables: objects (one row per real object: mean position, motion in arcsec per year, passes seen, Gaia id or none, colour D6/D1) and suspects (object id, kind: mover / unmatched / red / variable, score).

contracts/api.md · the endpoints

api summary
GET  /api/frames?ra=&dec=&fov=&det=1..6|fc&mode=blink|diff|sum
     → { passes:[{ pass, start, end, png, n_photos,
                   flags:{ satellite, ghost, cosmic } }],
         pixel_arcsec, fov_arcmin }
GET  /api/object?ra=&dec=
     → { name|null, gaia:{ id, pm_ra, pm_dec, parallax }|null,
         spectrum:[{ um, flux, err, det, mjd }],
         lightcurve:[{ mjd, det, flux, err }] }
GET  /api/suspects?box=ra1,dec1,ra2,dec2&kind=&minspeed=&unknown=1
GET  /api/resolve?name=          # name → position now
# votes: browser → Firestore collection "votes"
#   { suspect_id, answer: real|junk|unsure, ts, voter }

# pass rule (everyone uses this)
pass = max(1, floor((mjd - 60796) / 182.6) + 1)
# 60796 = 1 May 2025, start of the sky survey

Workflow

How we work with Claude Code

  1. Plan before codeStart each task in plan mode (Shift+Tab until it says plan mode). Read the plan and correct it before Claude edits anything.
  2. Point at the contractEvery first message names the contract file and the fixtures to use. That's what keeps the four areas compatible.
  3. One branch per taskName it after your area, like p2/frames-endpoint. Open a PR into main; the lead merges at least every hour.
  4. Two tasks at onceRun claude -w <name> to get a separate copy of the repo on its own branch, so parallel sessions don't overwrite each other.
  5. Sync oftenRun /sync before every new task, and /contract-check before every PR.
  6. Side jobs in the backgroundTests, docs and small refactors can go to Claude Code on the web (claude.ai/code) on the same repo. It opens its own branch and PR.
  7. No keys in chatNever paste passwords or key files into Claude. Google access comes from gcloud auth login.
  8. Stuck for 20 minutes?Tell the lead. Ask Claude for a short summary of the change for every PR description.

  1. Budget alerts

    Billing → Budgets & caps → Create budget. The form has four steps:

    StepWhat to set
    1 · DefineChoose Alerts only. Name: nasa-glazing hackathon. Next.
    2 · ScopeProjects: nasa-glazing. Services: all. Under Credits, untick "Promotions and others", or the €264 credit hides your spending and no alert ever fires. Next.

Ignore the approved "Committed N2D CPUs": it only applies to 1- or 3-year commitments, so never buy one.
