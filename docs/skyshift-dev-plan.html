Architecture

Static files first, a live API for everything else

The same Python function turns a sky position into blink frames. A script runs it ahead of time for the featured targets; Cloud Run runs it on request for any other coordinates and caches the result in the bucket. The site always tries the static files first.

Featured targets, static

The five test objects, comet 3I/ATLAS and two asteroids. scripts/precompute calls the blink function and writes web/public/data/<slug>/. They load at once and keep working after the credit ends. Barnard's Star, Epsilon Indi B and WISE 0855 are built from real data (PR #13, open); the rest are in progress.

Any coordinates, live

The site asks /api/frames. Cloud Run searches IRSA, fetches cutouts, stacks and measures with core/, and caches the result in cache/. Target: first frame under 15 s.

Hunt zone, gated

100 deg² on the ecliptic, 3,692 photos. A 12 deg² pilot (990 photos) runs first on the test machine. Only if gate G2 passes does the spot worker run the rest, for under an hour. Each photo's output file in dots/ marks it done. Steps: Pipeline.

# SkyShift

Web tool for NASA Space Apps 2026 "Planet X and SPHEREx". Paste coordinates and blink any spot of
NASA's SPHEREx sky on two clocks: visits six months apart, and exposures inside a visit.
Measure what moved and check it against Gaia and known asteroid positions.
Plans: docs/skyshift-hackathon-plan.html (what and why) · docs/skyshift-dev-plan.html (how).

## Domain facts
- Exposure = one SPHEREx photo (113 s). Session = 1–5 exposures 2.1 min apart.
  Visit = the 2–4 weeks in which SPHEREx sees one spot, every six months: about 21 sessions,
  55–60 exposures. Dates depend on the position. There are no fixed "passes".
- Visit rule: sort the exposure times at a position; start a new visit where the gap exceeds
  60 days; cut any visit longer than 75 days (near the ecliptic poles) into n = ceil(days / 30)
  equal parts. A session is a run with gaps under 10 minutes.
- Time: MJD-AVG from the IMAGE header (UTC, exposure midpoint). In search results, the middle
  of t_min and t_max. MJD-BEG and MJD-END also exist. DATE is the file creation time: never use it.
- Band: detector from energy_bandpassname ("SPHEREx-D2") or the header, never the filename.
  IMAGE header DETECTOR: 1–3 SWIR, 4–6 MWIR. The name suffix _<exp>D<det> (e.g. _2D1) agrees,
  but never parse names.
- 6 detectors: D1 0.75–1.1, D2 1.1–1.6, D3 1.6–2.4, D4 2.4–3.8, D5 3.8–4.4, D6 4.4–5.0 µm.
  102 channels in all. Pixel 6.15″ (6.152″ measured). PSF FWHM 7.53″. Images 2040 × 2040.
  DETCOORD = 'sky': MWIR pixels are already flipped on X to match the SWIR view.
- D1+D4, D2+D5, D3+D6 are exposed at the same moment: a D1→D4 flip is colour, not motion.
  Compare brightness only within one detector.
- A file is one FITS: IMAGE, FLAGS, VARIANCE, ZODI, EPSF, WCS-WAVE, 60.2 MB (measured). The
  pipeline streams all six parts once (~56 MB) and keeps ~4.5 MB of computed data per photo.
  FLAGS is a tile-compressed HDU: let astropy decode it. ZODI is not subtracted from IMAGE.
- Units: IMAGE is in MJy/sr (BUNIT 'MJy / sr', float32). 1 MJy/sr = 889 µJy in a 6.15″ pixel.
  TELAPSE 118 s from start to stop. Aperture correction at r = 2 px: 1.033 (from the ePSF).
- Flags (contracts/flags.md). Mask for detection and photometry: TRANSIENT, OVERFLOW, SUR_ERROR,
  NONFUNC, DICHROIC, MISSING_DATA, HOT, COLD, PHANMISS, NONLINEAR, PERSIST, STREAK, SNOWBALL.
  Record on the dot, don't mask: CROSSTALK, GHOST, GHOST_FPA, GHOST_EXT, BLOOM, HALO, OUTLIER.
  Never mask SOURCE (set on about 99% of pixels) or FULLSAMPLE.
  OVERFLOW or NONLINEAR in a source's core means saturated.
  Bit names and numbers confirmed on the first file (14 Nov). SOURCE was on 99.37% of pixels;
  the mask list removed about 2.1%.
- Saturation starts near AB 10–11 (to check on real data). Barnard's Star, RW Aurigae and
  R Draconis are expected to saturate: centroid on the wings and mark the core.
- Collections: spherex_dr1 and spherex_qr3. Skip *_deep. Search with astroquery Irsa.query_sia;
  the TAP table name is unverified.
- S3: s3://nasa-irsa-spherex (us-east-1, anonymous). Layout:
  <dr1|qr3>/level2/<planning period>/l2b-v<version>-<date>/<detector>/<file>.fits
  Cutouts (?center=RA,DEC&size=DEG, degrees) work on IRSA's servers only, not on S3.
- No CDS: SIMBAD, Aladin's CDN and CDS tiles are down. Aladin Lite 3.8.2 from jsDelivr,
  IRSA layer URLs only, SIMBAD features off. Names from our /api/resolve list.
- Targets (web/src/data/targets.json): Barnard's Star, Epsilon Indi B, WISE 0855−0714,
  RW Aurigae, R Draconis; plus comet 3I/ATLAS and two numbered asteroids.
  Move Gaia DR3 positions from epoch 2016.0 to each visit's mid-time.
- Docs: https://caltech-ipac.github.io/irsa-tutorials/ ·
  https://irsa.ipac.caltech.edu/data/SPHEREx/docs/SPHEREx_Expsupp.pdf

# frames are data, not pictures
# 16-bit arrays, at most 300 px a side; value = raw × scale + zero (MJy/sr)
# sampling is fixed per field; pixel_arcsec reports it:
#   months  5′  3× oversampled   2.05″/px   146 px
#   months 15′  2× oversampled   3.08″/px   293 px
#   hours  20′  native pixel     6.15″/px   195 px
#   hours  60′  binned 2×        12.3″/px   293 px
# the browser does stretch, invert, subtract and add

Frame sizes: the sampling is fixed per field so that no frame exceeds 300 px. A 15′ field at 3× would be about 440 px and a 60′ field at the native pixel about 585 px, so the 15′ field uses 2× and the 60′ field is binned 2×. P1 fixes the binary layout of data_url (proposal: raw little-endian uint16, north up, east left) at 09:00.

One Parquet file per photo in dots/, brightest first, never rewritten; its existence marks the photo done. Each file also carries the photo metadata (key skyshift_photo): spacecraft position and velocity, astrometry against Gaia, PSF size and shape, background and ZODI 32 × 32 grids, header quality values, stage timings. Beside it, forced/ holds the ePSF and 2 px fluxes at every reference-catalogue star, detected or not.

Pipeline · pipeline/ · P1

Read each photo once, then combine the tables

The heavy step reads every photo once and writes its dots. Everything after it works only on stored tables, never on photos again. The pilot is 12 deg² (990 photos from 352 exposures) on skyshift-test; the hunt zone is 100 deg² (3,692 photos) on skyshift-worker after G2. Rules and thresholds: pipeline/CLAUDE.md and config.py.

The data rule

NASA's photos are never copied. Each photo is streamed from s3://nasa-irsa-spherex over HTTPS without a login and read once: all six parts, about 56 MB. Dots, forced photometry and photo metadata all come out of that one read. We keep about 4.5 MB of computed data per photo (pilot ~4.5 GB, hunt zone ~17 GB).

Why combine afterwards

Photos are independent, so the dots step runs in parallel on every core. Each photo's file marks it done, so a stopped or reclaimed machine restarts where it was. The combining steps read only stored tables, so they re-run in minutes when a threshold changes, and nothing measured is lost. link, spectra, classify, photoz, score and suspects always recompute.

Measured in the design review (14 Nov)

  • A pilot position gets about 113 exposures in 38 sessions over two visits; 78.5% of sessions have 2 or more, so pairs inside a session really happen.
  • thresh=5 really meant S/N ~22 on SPHEREx's sharp PSF, so detection now runs at 2.0 (S/N ~9) and keeps S/N ≥ 5.
  • SkyBoT is queried once per session, not per photo.
  • One photo on the cloud: read 1.1 s, detect 8.6 s, 28,583 dots.

Known objects · decided 14 Nov

MPC orbits replace SkyBoT

We work out where every known asteroid and comet was in each photo ourselves, from the Minor Planet Center's orbit file and the open-source kete library, instead of asking the SkyBoT web service. It runs offline, has no rate limit, sees the sky from SPHEREx itself, and scales to the whole sky.

Who tells us what

SourceWhat it knowsWhat we use it forStatus
Gaia DR3 (ESA)1.8 billion stars: position in 2016, proper motion, parallax, brightness. Nothing on asteroids at our dates.Which dots are stars; how far a star should have moved (V2, V3); rings in the blink; distances on the cardskeep
MPC (Minor Planet Center, IAU)Orbits of about 1.5 million known asteroids, plus comets; updated dailyWhere each known asteroid or comet was at each photo's time, seen from SPHEREx; its expected Vnew
kete (Caltech/IPAC, BSD-3)Python library that loads MPC orbits, moves them with full n-body physics, and checks which fall inside a survey frame. Has a built-in SPHEREx frame type.The calculation behind the MPC stepnew
SkyBoT (IMCCE)Web service that does the same calculation on its servers, one cone at a time (13–23 s each), seen from the Earth's centreOnly as a cross-check on the pilot, then droppedreplaced
IRSA MOSTFor one named asteroid: which SPHEREx photos caught it and whereV4 test on asteroids 1–60keep

Why switch

  • Scale. The whole sky has about 100,000 sessions. At 13–23 s per SkyBoT cone that is hundreds of hours, and an unfair load on a free service. Local orbits take minutes to hours on our own machines.
  • Accuracy. SkyBoT answers from the Earth's centre. Each photo's header holds SPHEREx's own position and speed (X_SC, VX_SC…, already copied into every dot file), so we predict positions as SPHEREx saw them, at each photo's own MJD-AVG, with light-time correction.
  • No rate extrapolation. SkyBoT gives one position per session and we move it with its rates; kete computes each photo's time directly.
  • Offline and fixed. One dated copy of the orbits in the bucket, so every machine and every rerun uses the same catalogue.

What stays the same

  • The known step writes the same cache shape it writes today: per session, objects: {name, number, ra, dec, v, dra_arcsec_h, ddec_arcsec_h, class}. load_predictions, link, score and suspects don't change.
  • Matching rules: a known object within 2 px (about 12″) of a mover; suspects have no known object within 30″.
  • A config switch, KNOWN_SOURCE = "skybot" | "mpc", so the pilot can run both and compare.
  • Contract: known[].source gains "mpc" in contracts/api.md (its own contract PR, P1).

Rules and compliance

What keeps the submission eligible

From the Space Apps FAQ, submission guide and terms. Any item that fails the check at the Saturday 22:00 save, or the Sunday 09:00 private-window check, gets fixed before anything else.

RuleWhat we do
No project code before Sat 09:00The FAQ says teams may not start work on the challenge before the hackathon. Accounts, quotas, installs and reading are preparation. The repo is created at 09:00 so its history starts at kickoff. The plan pages' simulated demo code is never reused.
AI disclosureThe project page and a README "Use of SI" section say plainly that Claude Code wrote most of the code from our instructions and helped with research, planning and text, and that we reviewed and tested it. Commits keep their Co-Authored-By line. The idea and the decisions are the team's. The draft text is on the concept page.
Screen recordings onlyEvery image, GIF and video is a screen recording of the running tool on real data. No AI-generated media, so no watermark is needed. No NASA logos. The S4 planted-object drill is cut; anything simulated that is ever shown is labelled as such.
Video 30 s or lessCut to 29.0 s, and check the length with a tool before upload: ffprobe -v error -show_entries format=duration -of csv=p=0 skyshift.mp4. The seven slides are the fallback demo.
Public repo and linksThe repo is public from the first commit. The video and live site links are tested in a private window: no password, permission or sign-in.
Licence Apache-2.0In LICENSE from the first commit. Every outside library and data source is listed on the page, with its licence where it matters (Aladin Lite is GPL-3.0).
NASA and partner dataSPHEREx from IRSA is the NASA source. ESA Gaia DR3 is partner data. Copy the SPHEREx acknowledgement and its two citations word for word from IRSA's mission page.
