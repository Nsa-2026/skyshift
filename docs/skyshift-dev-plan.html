Changed since v1

  • No "passes". We blink on two clocks: Months (one stacked frame per visit, six months apart) and Hours (single exposures inside a visit).
  • Static first. Featured targets are files on Firebase Hosting; the live API serves any other coordinates.
  • The 5% deep zone is cut. A 100 deg² hunt zone runs only if gate G2 passes at Sat 18:00.
  • Frames are 16-bit data, not pictures. The browser does stretch, invert, subtract and add.
  • No CDS: Aladin Lite 3.8.2 from jsDelivr, IRSA layer URLs only, SIMBAD features off.

Architecture

Static files first, a live API for everything else

The same Python function turns a sky position into blink frames. A script runs it ahead of time for the featured targets; Cloud Run runs it on request for any other coordinates and caches the result in the bucket. The site always tries the static files first.

Featured targets, static

The five test objects, comet 3I/ATLAS and two asteroids. scripts/precompute calls the blink function and writes web/public/data/<slug>/. They load at once and keep working after the credit ends.

Any coordinates, live

The site asks /api/frames. Cloud Run searches IRSA, fetches cutouts, stacks and measures with core/, and caches the result in cache/. Target: first frame under 15 s.

Hunt zone, gated

100 deg² on the ecliptic, about 3,400 photos. A 12 deg² pilot runs first on the test machine. Only if gate G2 passes does the spot worker run the rest, for under an hour. Each photo's output file in dots/ marks it done.

CLAUDE.md (repo root)
# SkyShift

Web tool for NASA Space Apps 2026 "Planet X and SPHEREx". Paste coordinates and blink any spot of
NASA's SPHEREx sky on two clocks: visits six months apart, and exposures inside a visit.
Measure what moved and check it against Gaia and known asteroid positions.
Plans: docs/skyshift-hackathon-plan.html (what and why) · docs/skyshift-dev-plan.html (how).

## Areas and owners

- pipeline/            Pilot and hunt zone on the cloud machines. P1.
- scripts/validate/    V1–V8, writes web/public/data/validation.json. P1.
- server/              FastAPI on Cloud Run. build_blink() for any coordinates. P2.

## Domain facts
- Exposure = one SPHEREx photo (113 s). Session = 1–5 exposures 2.1 min apart.
  Visit = the 2–4 weeks in which SPHEREx sees one spot, every six months: about 21 sessions,
  55–60 exposures. Dates depend on the position. There are no fixed "passes".
- Visit rule: sort the exposure times at a position; start a new visit where the gap exceeds
  60 days; cut any visit longer than 45 days (near the ecliptic poles) into 30-day bins.
  A session is a run with gaps under 10 minutes.
- Time: MJD-AVG from the IMAGE header (UTC, exposure midpoint). In search results, the middle
  of t_min and t_max.
- Band: detector from energy_bandpassname ("SPHEREx-D2") or the header, never the filename.
- 6 detectors: D1 0.75–1.1, D2 1.1–1.6, D3 1.6–2.4, D4 2.4–3.8, D5 3.8–4.4, D6 4.4–5.0 µm.
  102 channels in all. Pixel 6.15″. Images 2040 × 2040.
- D1+D4, D2+D5, D3+D6 are exposed at the same moment: a D1→D4 flip is colour, not motion.
  Compare brightness only within one detector.
- A file is one FITS: IMAGE, FLAGS, VARIANCE, ZODI, EPSF, WCS-WAVE, about 66 MB. We read IMAGE,
  FLAGS and WCS-WAVE: an estimated 28 MB, to be measured.
- Units: IMAGE is in MJy/sr. 1 MJy/sr = 889 µJy in a 6.15″ pixel.
- Flags (contracts/flags.md). Mask for detection and photometry: TRANSIENT, OVERFLOW, SUR_ERROR,
  NONFUNC, DICHROIC, MISSING_DATA, HOT, COLD, PHANMISS, NONLINEAR, PERSIST, STREAK, SNOWBALL.
  Record on the dot, don't mask: CROSSTALK, GHOST, GHOST_FPA, GHOST_EXT, BLOOM, HALO, OUTLIER.
  Never mask SOURCE (set on about 99% of pixels) or FULLSAMPLE.
  OVERFLOW or NONLINEAR in a source's core means saturated.
- Saturation starts near AB 10–11 (to check on real data). Barnard's Star, RW Aurigae and
  R Draconis are expected to saturate: centroid on the wings and mark the core.
- Collections: spherex_dr1 and spherex_qr3. Skip *_deep. Search with astroquery Irsa.query_sia;
  the TAP table name is unverified.
- S3: s3://nasa-irsa-spherex (us-east-1, anonymous). Layout:
  <dr1|qr3>/level2/<planning period>/l2b-v<version>-<date>/<detector>/<file>.fits
  Cutouts (?center=RA,DEC&size=DEG, degrees) work on IRSA's servers only, not on S3.
- No CDS: SIMBAD, Aladin's CDN and CDS tiles are down. Aladin Lite 3.8.2 from jsDelivr,
  IRSA layer URLs only, SIMBAD features off. Names from our /api/resolve list.
- Targets (web/src/data/targets.json): Barnard's Star, Epsilon Indi B, WISE 0855−0714,
  RW Aurigae, R Draconis; plus comet 3I/ATLAS and two numbered asteroids.
  Move Gaia DR3 positions from epoch 2016.0 to each visit's mid-time.
- Docs: https://caltech-ipac.github.io/irsa-tutorials/ ·
  https://irsa.ipac.caltech.edu/data/SPHEREx/docs/SPHEREx_Expsupp.pdf

# frames are data, not pictures
# 16-bit arrays, at most 300 px a side; value = raw × scale + zero (MJy/sr)
# sampling is fixed per field; pixel_arcsec reports it:
#   months  5′  3× oversampled   2.05″/px   146 px
#   months 15′  2× oversampled   3.08″/px   293 px
#   hours  20′  native pixel     6.15″/px   195 px
#   hours  60′  binned 2×        12.3″/px   293 px
# the browser does stretch, invert, subtract and add

Frame sizes: the sampling is fixed per field so that no frame exceeds 300 px. A 15′ field at 3× would be about 440 px and a 60′ field at the native pixel about 585 px, so the 15′ field uses 2× and the 60′ field is binned 2×. P1 fixes the binary layout of data_url (proposal: raw little-endian uint16, north up, east left) at 09:00.

Firestore · flags and votes

CollectionFields
candidatesra, dec, mjd, clock, source: "user" | "pipeline"
votescandidate_id, answer: mover | changing | junk | unsure, ts, voter

Rules are create-only: anyone may read and create; nobody may update or delete. Each create must have exactly these fields, with the right types and allowed values. voter is a random id kept in the browser, never a name or email. Pipeline suspects are written server-side with source: "pipeline".

Workflow

How we work with Claude Code

  1. Plan before codeStart each task in plan mode (Shift+Tab until it says plan mode). Read the plan and correct it before Claude edits anything.
  2. Point at the contractEvery first message names contracts/api.md (and flags.md or dots.md if relevant) and the fixtures to use. That keeps the four areas compatible.
  3. One branch per taskName it after your area, like p2/frames-endpoint. Open a PR into main. Owners merge their own area when tests pass; contract PRs wait for P1.
  4. Two tasks at onceRun claude -w <name>: a separate copy of the repo in .claude/worktrees/<name> on its own branch, so parallel sessions don't overwrite each other. That folder is gitignored.
  5. Sync oftenRun /sync before every new task, and /contract-check before every PR.
  6. Shared settingsAfter editing .claude/settings.json, run claude doctor to check the file before you push it.
  7. Log in on each machineThe laptop and the cloud VM each need their own login. On the VM over SSH, press c to copy the login URL, open it on your laptop and paste the code back. claude auth status checks it.
  8. Pro or higherEveryone needs a Claude plan with Claude Code: Pro, Max, Team or Enterprise. The free plan has none.
  9. No keys in chatNever paste passwords or key files into Claude. Google access comes from gcloud auth login.
  10. Stuck for 20 minutes?Tell P1. Ask Claude for a short summary of the change for every PR description.
